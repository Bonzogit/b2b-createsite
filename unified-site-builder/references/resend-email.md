# 统一 Resend 邮件后台

本文件要求生成的网站实现以下能力；不是已经存在的公共邮件服务，也不表示现有网站已经改造。默认同一个所有者的多个网站使用其 Resend 账户，每站使用可独立撤销的发送密钥；不同客户保持账户/域名权限隔离。

## 后台界面

菜单：设置 → 邮件通知。中文字段与操作：

| 项目 | 行为 |
|---|---|
| 启用询盘通知 | 默认关闭，完成配置和测试后管理员开启；不影响保存询盘 |
| 邮件服务 | Resend |
| 通知收件邮箱 | 一个或多个管理员配置的真实邮箱，来源同 settings.contact.notificationRecipients |
| 发件人名称 | 网站/品牌名，标题另带站点和询盘编号 |
| 发件邮箱 | 使用该账户有权发送的已验证域名，校验格式，不允许客户表单控制 |
| 回复地址 | 内部通知默认使用该条询盘经过验证的客户邮箱作为 Reply-To |
| API Key | 密码输入；只允许保存、替换、移除，不回显原密钥；已有环境凭据显示来源 |
| 保存设置 | 只保存，不自动向客户发送邮件 |
| 检查配置 | 检查所需字段、密钥存储和可用证据，不假装完整凭据有域名管理权限 |
| 发送测试邮件 | 管理员明确点击后发到已保存的通知收件邮箱，限速并防重复 |
| 我已收到测试邮件 | 对应测试编号确认，记录时间与配置版本 |
| 通知记录 | 显示询盘编号、发送状态、时间、可理解的错误和人工重试 |

公开显示邮箱、通知收件邮箱、发件邮箱是不同用途。QQ/Gmail/企业邮箱可以作为收件地址；不能把不属于自己的公共邮箱域名当作 Resend 发件域名。

## 初次设置与域名

1. 管理员使用自己的 Resend 账户添加可控制的发信域名/子域名，并按其界面提供的 DNS 记录完成验证。
2. 创建发送权限 API Key；优先限制到选定发信域名，每站独立密钥。不把全权限账户密钥分发到每个站点。
3. 在网站后台填写发件信息、通知收件人及发送密钥，保存并发测试邮件，实际检查收件箱。
4. 只有管理员确认当前配置的测试邮件实收，才标记“收件已验证”。更换密钥、发件人或收件人后清除该验证状态，重新测试。

网站域名和发信域名可以不同：用临时网站地址时，也可使用账户下自己已验证的发信域名。不能验证自己不控制的 workers.dev/trycloudflare.com 子域作为发信域。无自有已验证域名时不能承诺正式发信已通；Resend 的默认 resend.dev 发件身份只适用于受限制的测试。
一个已验证的发信域可以为同一所有者的多个站点通知使用，在发件名称、主题与内部任务中区分站点；域名数量与发送额度按实际账户计划核对，不按站点数重复计算。
验证 DNS 是首次接入的独立步骤，不能只在网站后台填一个邮箱就声称自动通过。没有 DNS 管理授权时提供准确配置引导，不自行修改记录。保留现有邮箱接收记录。

## 凭据保存

管理员通过 HTTPS 后台提交密钥，不发到聊天。后台接口鉴权、CSRF、限速，关闭请求体日志与浏览器持久保存；响应只含 credentialConfigured 与来源等状态。
推荐持久秘密存储或部署注入。若后台支持直接保存密钥到数据库，使用经过验证的加密方式，例如 AES-GCM 和每次独立随机 nonce；加密主密钥来自服务器环境/Cloudflare Secret，不能和密文一起存入数据库、公开目录或普通内容导出。完整备份说明独立的主密钥恢复/轮换方法。
没有可用秘密存储/主密钥时，后台不接受明文落库，明确引导由部署环境配置 RESEND_API_KEY；之后其他邮件设置仍由后台管理。Cloudflare Worker 不能因为存在设置表单就假设自己能修改 Secret 绑定。
env 与后台凭据二选一，记录 credentialSource；若环境托管则 UI 显示受部署管理，不能让保存的新密钥看似生效却实际仍用旧值。业务日志、错误、导出和 ZIP 不包含密钥。

## 发送与可靠性

后端使用 Resend HTTPS API 或固定版本官方 SDK。收件人取管理员保存的配置；发件身份由服务端决定；内部通知 Reply-To 为客户邮箱，不能用客户邮箱作为 From。主题拒绝 CR/LF，内容 HTML 转义并提供文本正文。
通知包含站点名、询盘编号、必要需求及后台详情链接。私密附件提供需登录的后台链接，不附公开可访问 URL。客户确认邮件另设开关，默认关闭，不使用访客表单作为任意邮件转发器。
保存询盘时同时持久化邮件任务，响应不等待外部发信；任务执行必须使用该运行环境可靠的调度/持久队列。重试使用稳定幂等键和站点隔离，处理超时后不确定结果，按当前官方规则核对幂等期限。限次退避和人工重试，记录 emailId 与错误分类。
状态分开：未配置、已配置待测试、已提交测试、收件已验证；单封邮件按 unconfigured/queued/sending/submitted/failed 等业务协议显示。API 成功只表示服务商接受，不自动标记收件或阅读。
发送权限密钥不一定能列域名或读取邮件状态，不能因为这些请求被拒就断言发送密钥无效，也不能因此要求升级全权限。通过合法测试发送和收件确认完成验证。需要送达 Webhook 时另外配置签名校验、重放防护、事件去重和站点归属；未接通不伪造 delivered。
失败通知不丢询盘，后台可继续处理，额度不足不自动购买。配置关闭/更换收件人时明确未发送任务的处理方式，不将旧询盘自动群发给新收件人。

## 需实现的管理接口

在 /api/v1 下：
- GET/PUT /admin/email-settings：读写普通设置、只写凭据及配置版本；读取不返回密钥。
- POST /admin/email-settings/check：非发信配置检查，返回可检查项与未知项。
- POST /admin/email-settings/test：管理员主动触发，只发到保存的内部收件人，返回测试 ID 与 submitted/pending/failed。
- POST /admin/email-settings/confirm-test：确认对应配置版本与测试 ID 的人工实收结果。
- GET /admin/email-events：仅本网站通知记录，脱敏且不泄漏秘密。

## 网站检查与已授权测试

检查网站时先读取会话或项目的已有授权与安全凭据，复用获准的测试地址；本文件不保存个人邮箱、账户密钥或本机凭据路径。缺少必要登录条件时仅询问缺项，不重复请求已有授权。

- 优先复用当前自有已验证发信域名；临时网址使用所有者授权的已验证域名，不把 IP、workers.dev 或 trycloudflare.com 当作可验证的自有发信域。新增自有域名须等 DNS 验证后发信，保留已有邮箱 DNS。
- 测试只发给已授权测试地址，不发给真实客户。测试地址不覆盖网站现有 notificationRecipients，也不因测试开启客户确认邮件。生产接口只支持已保存内部收件人时，在隔离工程使用测试配置；不得临时修改生产收件人或放开公开任意收件接口。
- 服务商单独发信检查与网站完整流程分开：后者需验证询盘/附件入库、任务执行及通知状态。生产通知仍指向真实业务邮箱时，不以测试询盘触发该邮箱发信；使用隔离数据与配置验证。
- 分别记录 API 接受、可信送达事件或人工实收、询盘持久化、通知代码完整流程；没有送达/实收证据就写未验证，不伪造确认。

## 验收

必须验证保存不回显密钥、无配置仍收单、公开请求不能触发测试/任意收件、错误密钥/域名/限额明确失败、重试不重复、配置变更清除旧验证、升级后配置保留。模拟测试不等于真实邮件收件通过。首次实收测试需要已有有效授权的目标地址和发信操作；会话已授权时直接复用。
